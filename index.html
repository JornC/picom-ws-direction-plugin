ws-direction

A picom plugin that tells your animation scripts which way an i3 workspace switch went, and which monitor the workspace is on. Windows slide the right way, and stay on their own monitor.

It needs a picom with plugin API 0.2, which no release has yet; see Install.

Styles

The plugin only hands picom numbers; the animation itself is a few lines of config, so it can look however you like. Seven styles come with it, and one line in picom.conf picks one. Change the name and save; picom reloads by itself.

@include "ws-direction/fold.conf"

Each style has a var-length near the top, in seconds; make it larger for a slower switch.

What your scripts get

The plugin adds five variables, which scripts read like window-width. picom asks the plugin for their values when an animation starts, and only for scripts that use them.

plugin-ws-direction-direction
1 if the new workspace comes after the old one, -1 if it comes before, and 0 if the animation wasn't caused by a workspace switch on that monitor: a new window, the scratchpad, fullscreen, or a window moved to another workspace.
plugin-ws-direction-monitor-x, -y, -width, -height
The monitor that shows the window's workspace. Crop a slide to it, so it doesn't spill onto your other monitor.

Workspaces are ordered as in _NET_DESKTOP_NAMES. Under i3 that means by workspace number, with unnumbered names last.

How a style uses them

A simplified part of the slide style: what happens when a window shows on a landscape monitor.

# Start one monitor height away, on the side the switch
# came from, and move back to 0 in a quarter second.
var-pos = {
  duration = 0.25;
  start = "plugin-ws-direction-direction";
  end = 0;
};
offset-y = "var-pos * plugin-ws-direction-monitor-height";

# Cut the window off at the edges of its own monitor,
# so it never slides onto the other one.
crop-x = "plugin-ws-direction-monitor-x";
crop-y = "plugin-ws-direction-monitor-y";
crop-width = "plugin-ws-direction-monitor-width";
crop-height = "plugin-ws-direction-monitor-height";

The full styles are in styles/; each file explains how it works.

Install

  1. Use a picom with plugin API 0.2, which adds the animation variable hook. No picom release has it yet: build picom from the hook-v2 branch, which is based on picom's next branch, with the hook added.
  2. Build the plugin and install it with its styles in ~/.config/picom: 
    make
make install
    To build against a picom source tree instead of the installed headers: 
    make PICOM_API_CFLAGS=-I/path/to/picom/include
  3. Load it in picom.conf and pick a style: 
    plugins = "ws-direction.so";
rules = ({
  match = "!override_redirect && window_type = 'normal'";
  @include "ws-direction/slide.conf"
});

An older picom logs ws-direction: picom is too old and runs without the variables.

How it works

picom knows when a window shows or hides, but not why. The plugin fills that gap from outside picom. It reads the window manager's EWMH properties (_NET_CURRENT_DESKTOP, _NET_DESKTOP_NAMES and _NET_DESKTOP_VIEWPORT on the root window, _NET_WM_DESKTOP on each window) and the monitors from RandR, and it remembers the recent workspaces of every monitor.

Window managers don't follow a fixed order when they update these properties and show or hide windows, so the plugin doesn't act on events. When a window starts an animation that reads one of its variables, picom asks the plugin, and the plugin matches the window to a recent switch on its monitor. It reads the root window once per update pass, however many windows start animating in it.

Limits

  • Tested with i3.
  • With picom's xrender backend, cascade can flicker: during a switch, a window that is already moving in is sometimes not drawn for a frame or two. That is a bug in the xrender backend, not in the style; the glx backend doesn't have it, and with use-damage = false it doesn't happen either.
  • A switch made while picom isn't compositing (a fullscreen window with unredir-if-possible) can be missed. The next slide may then go the wrong way.
  • Each animation start waits for a reply from the X server: about 20 µs on a quiet server, a few milliseconds when it's busy.
