JornC/picom-ws-direction-plugin

ws-direction

A picom plugin that tells your animation scripts which way an i3 workspace switch went, and which monitor the workspace is on. Windows slide the right way, and stay on their own monitor.

What your scripts get

The plugin adds five variables, which scripts read like window-width. picom asks the plugin for their values when an animation starts, and only for scripts that use them.

workspace-direction
1 if the new workspace comes after the old one, -1 if it comes before, and 0 if the animation wasn't caused by a workspace switch on that monitor: a new window, the scratchpad, fullscreen, or a window moved to another workspace.
workspace-monitor-x, -y, -width, -height
The monitor that shows the window's workspace. Crop a slide to it, so it doesn't spill onto your other monitor.

Workspaces are ordered as in _NET_DESKTOP_NAMES. Under i3 that means by workspace number, with unnumbered names last.

A slide in your config

New workspaces slide in from below, old ones slide out the top, and both are cropped to their monitor:

animations = ({
  triggers = ["show", "open"];
  offset-y = {
    duration = 0.25;
    start = "workspace-direction * workspace-monitor-height";
    end = 0;
  };
  crop-x = "workspace-monitor-x";
  crop-y = "workspace-monitor-y";
  crop-width = "workspace-monitor-width";
  crop-height = "workspace-monitor-height";
}, {
  triggers = ["hide"];
  offset-y = {
    duration = 0.25;
    start = 0;
    end = "0 - workspace-direction * workspace-monitor-height";
  };
  crop-x = "workspace-monitor-x";
  crop-y = "workspace-monitor-y";
  crop-width = "workspace-monitor-width";
  crop-height = "workspace-monitor-height";
});

The full example, examples/picom-wsdir.conf, also fades windows that aren't part of a switch, and slides sideways on a second monitor. It's the config in the demo.

Install

  1. Use a picom with plugin API 0.2, which adds the animation variable hook. No picom release has it yet: build picom from the hook-v2 branch, which is picom's next branch with the hook added.
  2. Build the plugin: 
    make
    To build against a picom source tree instead of the installed headers: 
    make PICOM_API_CFLAGS=-I/path/to/picom/include
  3. Load it in picom.conf, and add animations that read the variables: 
    plugins = "/path/to/build/ws-direction.so";

An older picom logs ws-direction: picom is too old and runs without the variables.

How it works

picom knows when a window shows or hides, but not why. The plugin fills that gap from outside picom. It reads the window manager's EWMH properties (_NET_CURRENT_DESKTOP, _NET_DESKTOP_NAMES and _NET_DESKTOP_VIEWPORT on the root window, _NET_WM_DESKTOP on each window) and the monitors from RandR, and it remembers the recent workspaces of every monitor.

Window managers don't follow a fixed order when they update these properties and show or hide windows, so the plugin doesn't act on events. When a window starts an animation that reads one of its variables, picom asks the plugin, and the plugin matches the window to a recent switch on its monitor. It reads the root window once per frame, however many windows start animating in it.

Limits

  • Tested with i3.
  • A switch made while picom isn't compositing (a fullscreen window with unredir-if-possible) can be missed. The next slide may then go the wrong way.
  • Each animation start waits for a reply from the X server: about 20 µs on a quiet server, a few milliseconds when it's busy.
